# 04 基盤を使う

プロジェクトの管理者向け。基盤にプロジェクトを載せるために守る約束と、共有の DB を使うときの注意を書く。

約束は、コンテナを動かしてもらうのに要る最小限だけにしてある（[01](01_purpose.md) §4）。ここに書いていないこと（言語・フレームワーク・コンテナの数と構成・手元の開発環境・テスト・アプリの監視）は、プロジェクトが自由に決める。

## 1. 基盤に伝えること

プロジェクトを載せるときは、基盤の管理者に次を伝え、プロジェクトの一覧に1項目足してもらう（[03](03_responsibilities.md) §3）。

| 項目 | 内容 |
|---|---|
| 名前 | プロジェクトの名前。英小文字・数字・ハイフン。DB・シークレット・ネットワークの別名など、基盤の中の名前はすべてこれから作る |
| リポジトリ | GitHub のリポジトリ。非公開でもよい |
| ドメイン | 外から受けるドメイン名。DNS の A レコードは、プロジェクトが基盤の VM の IP に向ける |
| 載せる VM | どの VM に載せるか |
| シークレット | 要るシークレットの名前と、その作り方（下の表）。名前は英大文字で始め、英大文字・数字・`_` だけを使う。`AFP_` で始まる名前は基盤が使うので付けない |

| シークレットの作り方 | 意味 |
|---|---|
| `generate` | Vault が値を生成する。人は値を見なくてよい（署名の鍵など） |
| `manual` | 仮の値で作られる。プロジェクトが本当の値を Vault に入れる（外部の API キーなど） |

- DB のパスワードは、書かなくても基盤が必ず作る。英字・数字と、URL でそのまま使える記号（`-`・`_`・`.`・`~`）だけで作るので、接続の URL にそのまま埋め込める。
  - 記号を必ず含めるのは、MySQL HeatWave がパスワードに記号を1つ以上求めるため（`validate_password`）。英数字だけではユーザを作れない。

## 2. プロジェクトのリポジトリに置くもの

プロジェクトのリポジトリに **`compose.afp.yaml`**（Docker Compose の形式）を置く。基盤はこれを使ってコンテナを動かす。守ることは次の4つだけ。

1. **外から受けるサービスを1つ決める**。そのサービスを `afp` ネットワーク（基盤が用意する外部のネットワーク）に、**プロジェクトの名前を別名にして** 参加させ、**8080 番** で HTTP を待ち受ける。HTTPS は基盤の入口が受けるので、アプリは HTTP だけでよい。
   - **`afp` に入れるのは、このサービスだけ** にする。`afp` には全プロジェクトの入口のサービスが集まり、サービスの名前（`web`・`redis` など）がぶつかると、別のプロジェクトのコンテナにつながりうる。
   - DB は VM の外にあるので、`afp` に入れなくても、どのサービスからも §3 の値で接続できる。
2. **各サービスに `healthcheck` を書く**。基盤のデプロイは、すべてのサービスが健康になるのを待ち、ならなければ前の版に戻す。何を確かめるかはプロジェクトが決める。
3. **各サービスに `mem_limit` を書く**。小さい VM を1つのプロジェクトが使い切らないようにするため。
4. **環境で変わる値は、すべて環境変数で受ける**。ドメインもパスワードもファイルに書かない。だから `compose.afp.yaml` は公開してもよい。

最小の形は次のとおり。

```yaml
services:
  web:
    image: ${AFP_IMAGE_PREFIX}/web:${AFP_TAG}
    environment:
      DATABASE_URL: mysql://${AFP_DB_USER}:${AFP_DB_PASSWORD}@${AFP_DB_HOST}:${AFP_DB_PORT}/${AFP_DB_NAME}
      SIGNING_KEY: ${SIGNING_KEY}
      BASE_URL: https://${AFP_DOMAIN}
    healthcheck:
      test: ["CMD", "wget", "-q", "-O-", "http://127.0.0.1:8080/"]
    mem_limit: 128m
    networks:
      afp:
        aliases: ["${AFP_PROJECT}"]
networks:
  afp:
    external: true
```

- `AFP_TAG` は、デプロイする版の名前。プロジェクトが push したタグの名前そのもの。
- `AFP_IMAGE_PREFIX` の形と、ビルドの手順（OCI DevOps の `build_spec.yaml`）の書き方は、基盤を作りながら確かめて決める（未決）。
- 動く見本は、基盤のリポジトリの `examples/hello` に置く。

## 3. 基盤が渡す値

デプロイのたびに、基盤は次の値を、`docker compose` を動かすときの変数として渡す。`compose.afp.yaml` の中で `${変数}` として使える。コンテナの中で使うには、§2 の例のように `environment` に書いて渡す。

| 変数 | 中身 |
|---|---|
| `AFP_IMAGE_PREFIX` | イメージの置き場所（形は未決。§2） |
| `AFP_TAG` | デプロイする版（タグの名前） |
| `AFP_PROJECT` | プロジェクトの名前 |
| `AFP_DOMAIN` | プロジェクトのドメイン |
| `AFP_DB_HOST`・`AFP_DB_PORT` | DB の接続先 |
| `AFP_DB_NAME`・`AFP_DB_USER`・`AFP_DB_PASSWORD` | プロジェクトのデータベース・ユーザ・パスワード |
| シークレットの名前（例: `SIGNING_KEY`） | §1 で伝えたシークレットの値 |

## 4. そのほかの約束

- **マイグレーションはアプリが行う**（起動時など）。基盤はデプロイの直前に DB のダンプを取るだけで、マイグレーションには関わらない。
- **DB への接続の数を小さくする**（接続プールで数本）。DB の接続の上限は、全プロジェクトで共有している。
- **VM の中にファイルを残さない**。VM はいつ作り直されてもよいようにしてある（[02](02_architecture.md) §4）。アプリが受け取ったファイルを残すなら、プロジェクトが自分で Object Storage などに置く。
- **イメージは、載せる VM の CPU の種類で動くように作る**。今の VM は amd64。
- **DB の文字コードは `utf8mb4`、既定の照合順序は `utf8mb4_ja_0900_as_cs_ks`**。基盤はこれを既定にしてデータベースを作る。表や列ごとに替えるのはプロジェクトの自由。
  - 濁点・半濁点・ひらがなとカタカナ・大文字と小文字・小書きの文字（「ゃ」と「や」）を区別し、全角と半角だけを同じとみなす。並び順は日本語の順。
  - 理由: MySQL の既定（`utf8mb4_0900_ai_ci`）は「ハ」「バ」「パ」も「は」「ハ」も同じとみなし、一意制約で別の言葉がぶつかる。全角と半角は、利用者が打ち分けを意識しないことが多いので同じとみなす。
  - 採らなかった案: `utf8mb4_0900_as_cs`（全角と半角も区別する）・`utf8mb4_ja_0900_as_cs`（ひらがなとカタカナを同じとみなす）・`utf8mb4_bin`（並び順が人の感覚と合わない）。比べた結果は [references/mysql-notes.md](references/mysql-notes.md) §2。
- **手元の開発では、基盤のリポジトリの `mysql/VERSION` の版の公式の `mysql` のイメージに、`mysql/heatwave.cnf` を読ませる**。本番と振る舞いが変わる設定（`partial_revokes`・時差・既定の照合順序など）を揃えてある。

MySQL でアプリを書くときに、ほかの DB との違いで気を付けることは [references/mysql-notes.md](references/mysql-notes.md) にまとめてある。
