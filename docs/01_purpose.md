# 01 目的と方針

## 1. 前提: OCI の無料枠

OCI（Oracle Cloud Infrastructure）には、期限なく無料で使える **Always Free** という枠がある。お試し期間のクレジットとは別のもので、期間が終わっても残る。

この枠には、常時動かせる VM・マネージドの DB（MySQL HeatWave など）・オブジェクト・ストレージ・シークレットの保管庫・監視と通知などが含まれる。個人開発の小さな Web アプリなら、これだけで本番を動かせる。

一方で、枠は「VM は何台まで」「DB は何個まで」と **個数** で決まっている（値は [references/oci-free-tier.md](references/oci-free-tier.md)）。

## 2. 解きたい問題

個人開発のプロジェクトは、どれも小さい。利用者は本人か数人で、アクセスはわずかしかない。

それでも、プロジェクトごとに VM を1台と DB を1つ用意すると、次の問題が起きる。

- **無料枠の個数をすぐに使い切る**。1 プロジェクトで 1 組を使うと、載せられるプロジェクトは数個で止まる。
- **資源の大半が遊ぶ**。小さなアプリは、VM の CPU・メモリも DB の容量も、ほんの一部しか使わない。
- **同じ仕組みを毎回作る**。入口と証明書・デプロイ・DB の用意を、プロジェクトごとに作り、保つことになる。

## 3. この基盤がすること

**各プロジェクトのコンテナを受け取り、動かす**。基盤の仕事はこれに尽きる。

- 少ない VM に、複数のプロジェクトのコンテナを並べて動かす。
- コンテナを動かすのに欠かせないものだけを、共通で用意する。
  - 外からの入口（HTTPS と証明書・ドメイン名での振り分け）
  - 共有の DB の中の、プロジェクトごとのデータベースとユーザ（DB そのものの保守とバックアップは基盤が行う）
  - DB の接続先とシークレットを、環境変数としてコンテナに渡すこと
  - push されたものを本番に届けること（デプロイ）
- **プロジェクトの中身には立ち入らない**。言語・フレームワーク・コンテナの構成・手元の開発環境・テスト・アプリの監視は、プロジェクトが自由に決める。

プロジェクトが守るのは、コンテナを動かしてもらうための最小限の約束だけ。基盤はプロジェクトの中身を知らないので、**基盤は公開し、プロジェクトは非公開のまま載せられる**。

## 4. 方針

判断に迷ったときは、上から順に優先する。

1. **快適な開発と自動化**
   - プロジェクトは、タグを push すれば本番に届く。くり返す作業に人の手を要さない。
   - プロジェクトが手元で本番と同じ条件を再現できるよう、基盤は本番の条件（DB の版と設定・渡す環境変数）を明かす。
2. **仕組みの単純さ**
   - ここで言う単純さは、使い方の簡単さではなく、**基盤の設計と仕組みそのものの単純さ** を指す。
   - 部品が少なく、見て分かり、自分で直せること。複雑な仕組みは維持できない。
   - 「自動化」の名で部品を増やさない。まれにしか起きないことは手作業でよい。
   - 自動化の仕組みは基盤が1回だけ作り、プロジェクトを足すたびに増える作業を最小にする。
3. **費用の小ささ**
   - 無料枠を優先する。ただしゼロにこだわらず、便利さや単純さに見合う少額は払う。

あわせて、次を設計の前提にする。

- **プロジェクトに自由度を残す**。約束は、コンテナを動かしてもらうのに要る最小限にとどめる。基盤の都合でプロジェクトの作りを縛らない。
- **VM はステートレスにする**。失って困るものを VM に置かない。VM が消えても、作り直せば自動で元に戻る。
- **同じ働きなら OCI のサービスを使う**。
  - 基盤は OCI の上に作るので、DB・シークレットの保管・監視・デプロイなども OCI の中でそろえる。
  - OCI の中のサービスどうしなら、VM に与えた OCI の権限だけで互いを使え、Terraform でまとめて作れる。
  - OCI の外のサービスを混ぜると、サービスごとにアカウント・権限・接続用の認証情報・料金の管理が増える。
- **基盤の管理者とプロジェクトの管理者の責任を、明確に分離する**。
  - 同じ人が両方を担う場合でも、どちらが何を受け持つかをはっきり分ける。
  - 両者がやり取りするものを、約束として決める。

## 5. 向く使い方と向かない使い方

| 向く | 向かない |
|---|---|
| 個人や少人数で使うアプリ | 多くのアクセスを受けるアプリ |
| 多少止まってもよいもの（VM が1台なら、落ちると全プロジェクトが止まる） | 高い可用性が要るもの |
| 自分（たち）のプロジェクトを並べる | 他人のプロジェクトを預かる（プロジェクトの間の分離は、コンテナと DB のユーザの分離にとどまる。同じ VM のプロジェクトの入口のコンテナどうしは、基盤の入口を通らずに互いに届く） |
| コンテナで動く Web アプリ | 重い処理・大きなファイル・GPU を使うもの |

## 6. 用語

| 用語 | 意味 |
|---|---|
| 基盤 | このリポジトリが作るもの。プロジェクトのコンテナを動かす VM と、それに欠かせない共通の仕組みの全体 |
| プロジェクト | 基盤に載せるアプリ。それぞれ自分のリポジトリを持つ |
| 基盤の管理者 | 基盤を立て、保つ役割 |
| プロジェクトの管理者 | プロジェクトを作り、基盤に載せる役割 |
| `afp` | 基盤のコマンド（AlwaysFreePlatform の略） |
| ステートレス | 失って困る状態を持たないこと。消して作り直しても同じに戻る |
